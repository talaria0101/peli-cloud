# SSH into a sealed sandbox over an outbound-only relay

**Date:** 2026-10-02
**Host:** the errand sandbox (Linux x86_64, glibc, uid 0 with an empty capability
set, `bind(2)` INET refused, no `/etc/passwd`, no `/dev/ptmx`, no name resolver,
egress through a CONNECT proxy)
**Relay:** `tcp.ssh.relay.ajam.dev`, version `2026-10-01-r2`, reverse enabled
**Client/tool:** [`dropssh`](https://github.com/talaria0101/dropssh) `v0.2.3`,
release `dropssh-x86_64-linux-musl.tar.gz`
**Artefact:** `tools/ssh-relay-check.sh`, which reproduces this note from nothing
but the network. Its guard is `tests/ssh-relay-regressions.sh` (11 clauses).

## Result

```
relay=tcp.ssh.relay.ajam.dev name=p-<redacted> login=root shim=.dropssh-check/fakepwd.so
ssh_exit=0 marker=MARK:0:Linux
dropssh: registered with tcp.ssh.relay.ajam.dev as p-<redacted> (path /v1/node/p-<redacted>)
dropssh: relay hello: maxFrameBytes=65536 maxSessions=64
dropssh: operator opened session 446a1fbb (ready sent)
[3861] Child connection from unix:0
[3861] Pubkey auth succeeded for 'root' with ssh-ed25519 key SHA256:GmGk2tSQo... from unix:0
[3861] initgroups: Operation not permitted (continuing: gid unchanged)
[3861] Exit (root) from <unix:0>: Exited normally
PASS: a real ssh login ran over the outbound-only relay
```

The command run over the session was `id -u` and `uname -s`, returning `0` and
`Linux`. `id -u` is the load-bearing half: this cage has no `/etc/passwd`, so a
`0` from `id` can only come from a session where the login actually resolved an
account. Tokens are redacted here and are never echoed by the script.

## The host conditions, each measured

| condition | measurement |
|---|---|
| no inbound TCP | `bind(2) INET` on loopback refused with `EACCES`; `AF_UNIX` bound a socket. `sandhome report` prints `bind=unix`. |
| no passwd database | `ls /etc/passwd` -> "No such file or directory" |
| uid | 0, with `CapEff: 0000000000000000` — root that cannot `chown` |
| no pty | `/dev/ptmx` absent |
| no resolver | `getaddrinfo("railway.new")` -> "Temporary failure in name resolution" |
| egress | `169.254.169.1:40295` CONNECT proxy; HTTPS on 443 only |

The `CapEff` line is why the first failure was not a permissions story. This is
uid 0 and `chown(1001:1001, …)` still fails with `EINVAL`, so a root-only
explanation would have been wrong.

## What had to be true: five separate things

Each was a failure before it was a fix. Two of them are documented as
requirements in dropssh's own README and are not what actually works here, and
one of those two is documented wrongly.

**1. `tar` must be told `--no-same-owner`, or nothing is unpacked.** The
tarball carries uid/gid 1001 and GNU tar restores ownership by default. Every
entry fails with `Cannot change ownership to uid 1001, gid 1001: Invalid
argument` and tar exits non-zero, so the script dies before printing a single
diagnostic. Measured control: with the flag removed, `tools/ssh-relay-check.sh`
exits **2**; with it, exit **0** and a real login.

**2. The ssh client needs the `fakepwd` shim, and the reason is OpenSSH.**
`ssh(1)` maps its own uid before it sends anything, so with no `/etc/passwd` the
very first run died with `No user exists for uid 0` — from `ssh`, not from the
relay, and before a packet reached it. `LD_PRELOAD=fakepwd.so` with
`SANDHOME_PASSWD=<file>` supplies the entry. This shim is a separate concern from
the server's and needs a different justification than dropssh's docs give.

**3. `-Y FILE` is implemented in the released `dropbear` and is not in its help
text.** This one is documented backwards somewhere, and the error it causes is
silent, which is what makes it worth writing down.

- dropssh's README says the static server must be told its passwd database with
  `-Y`, and `patches/dropbear-passwd-file.patch` adds `case 'Y'`. That patch has
  been in the tree since commit `7523b2f`, tagged `v0.2.0` through `v0.2.3`.
- `dropbear -h` on the released `v0.2.3` binary **lists no `-Y`**.
- The binary **does** implement it. The proof is the patched code's own log
  string, which exists only if the patch was compiled in:
  `strings dropbear | grep 'passwd file'` matches, and a login with a name the
  file does not carry logs
  `passwd file '<path>': the file has no entry for that name`.

So a defensive `dropbear -h | grep -q -- '-Y'` probe looks like the careful
thing and is the opposite: it finds nothing, drops the flag, and removes the
only passwd path that works without the shim — and nothing complains. Filed as
[dropssh#14](https://github.com/talaria0101/dropssh/issues/14), which also
records a correction to the patch's own comment: it says *"the letter is unused
upstream"*, and upstream dropbear's `-Y` is the **master-password** option.
This repository's own issue #2 on that project recorded that and refused it,
because it logs the password in plaintext on startup and overwrites `pw_passwd`
for every session. The released binary does **not** contain that code (the
`Plaintext:` log string is absent), so the shipped `-Y` is the file-reading
option and the redefinition does work — but the comment reads as a factual
claim and is not one.

The guard
`release_dropbear_has_passwd_file_code_not_help_line` asserts the code is there
by the log string, not by the help text, and
`script_does_not_ask_for_a_passwd_flag_it_did_not_prove` fails if such a probe
is reintroduced.

**4. The passwd line's first field must be the name `ssh` logs in with, and the
server can refuse in two different ways.** With the file naming `subjectname`
and `ssh` offering `subjectname`, the login authenticates. Change only the
file's first field and the same login is refused, with a different line:

| passwd line names | ssh login | server log | exit |
|---|---|---|---|
| `subjectname` | `subjectname` | `Pubkey auth succeeded for 'subjectname'` | 0 |
| `someoneelse` | `subjectname` | `passwd file '…': the file has no entry for that name` | 255 |

A control cannot use a name the system database also knows: every login here is
uid 0 and `root` resolves through the shim, so "remove the entry" and "wrong
name" are indistinguishable unless the control names someone else. The clause
asserts both cells (`tests/assert-passwd-name.sh`).

**5. `-r`, `-D` and `-Y` are all required together, and the default cannot
start at all here.** dropssh's built-in server command is `dropbear -i -E -F`;
its compiled-in host key paths are `/etc/dropbear/dropbear_*_host_key` and do
not exist in this cage. `-r` and `-D` supply the host key and the
`authorized_keys` directory.

Both passwd paths are kept rather than one. Measured on this host:

| server environment | result |
|---|---|
| `-Y <file>`, no shim in the environment | `Pubkey auth succeeded`, exit 0 |
| shim, no `-Y` | `Login attempt for nonexistent user`, exit 255 |
| both | `Pubkey auth succeeded`, exit 0 |

Depending on one would make the check hostage to which mechanism a given
release carries.

## One dropssh defect this work found

**`dropssh doctor`'s server probe resolves a relative `--server` against the
probe's own cwd**, so it reports a false negative about the host. Measured
2026-10-02, `v0.2.3`:

| cwd | `--server` | doctor says |
|---|---|---|
| the work dir | `./dropbear -i -E -F -r <abs>/hostkey -D <abs>/ak` | `ok  the server starts  stayed up on a socketpair for 900ms` (6/6) |
| the repository root | the **same** relative command | `FAIL  the server starts  the command could not be started` (2/2) |
| the repository root | the command with an **absolute** binary path | `ok  the server starts` (2/2) |

`src/doctor.c`'s `check_server` runs the command with
`execl("/bin/sh", "sh", "-c", cmd)` in a child that keeps the parent's cwd, so
`./dropbear` resolves wherever the operator was standing. The consequence is
that a reader can be told their ssh server cannot start, on a host where a real
relay login works. The clause
`doctor_server_probe_needs_an_absolute_path` asserts the subject, the control
and the repair, so a dropssh release that changes this fails here rather than
the error returning quietly.

### A theory this note records because it was wrong

While isolating the above I claimed doctor was wrong in a deeper way: that its
`AF_UNIX` socketpair probe killed the server, because
`patches/dropbear-inetd-pipe-tolerance.patch` only tolerates `getpeername()`
failing with `ENOTSOCK` and a socketpair yields `EAFNOSUPPORT`. Measured
directly, it does not:

| fd 0 | result |
|---|---|
| `AF_UNIX` socketpair (what doctor does) | **ALIVE**, writes `SSH-2.0-dropbear_2026.94` |
| `/dev/null` | exits 1, `Early exit: Failed socket address: Not a socket` (`ENOTSOCK`) |

The patch catches the `/dev/null` case, which is why `/dev/null` exits and the
socketpair does not. The probe's design is correct; the cwd resolution is not.
The earlier draft of this note asserted the reverse and the assertion was
removed rather than kept as a caveat.

## The relay pair, and why no token is committed

`dropssh pair` calls the relay's self-service rendezvous endpoint
(`POST /v1/pair`) and returns a random name, a `node_token`, a `connect_token`
and a `stop_token`. The relay's own documentation states the trust model plainly:
the relay authenticates tokens, not people, and the connect token must reach the
operator over a trusted channel (TOFU).

That is a credential, so this repository does not carry one. The script mints a
fresh pair on every run, writes it mode 600 under `.dropssh-check/`, and never
prints it. Only public key material is generated. `.gitignore` excludes that
directory, and `no_committed_tokens` fails if any 64-hex string appears in the
files this work adds.

## Reproduce

```sh
sh tools/ssh-relay-check.sh          # exit 0 means a real login ran
sh tests/ssh-relay-regressions.sh    # 11 clauses; each names the control it needs
sh tests/one-login.sh <name>          # one login, with the passwd name drivable
```

`one-login.sh` is the harness the name clause is built on. `PASSWD_NAME=<n>`
changes only the passwd line's first field, so a subject and its control differ
in one word.

## Scope, stated honestly

- This proves the transport and the login. It does **not** claim the relay is
  private: the name and both tokens are bearer credentials and anyone who reads
  them can open a session.
- It does not run a server after the check exits. `--once` serves one session and
  the script kills the process; nothing here leaves a listening or dialing node
  behind.
- **⛔ WITHDRAWN, AND REPLACED BY A PROOF. The previous revision of this note
  claimed "the relay's forward path delivers the target's first bytes and then
  nothing, for any protocol". That was wrong, and I found the mistake by
  testing it with a client that shares no code with dropssh.**

  The relay's forward transport is healthy. `sh tools/poc-forward-relay.sh`
  demonstrates all of this in one run, exit 0:

  | # | measurement | result |
  |---|---|---|
  | 1 | the relay's own `/trace?target=railway.new:22&banner=1` | `verdict=live`, `bytes_seen=12`, `banner=SSH-2.0-Go` |
  | 2 | a raw RFC6455 client (no dropssh) to `example.com:80` | 320 bytes of a real HTTP 400 from Cloudflare |
  | 2 | the same client to `railway.new:22` | **690 bytes: the banner AND the server's KEXINIT** |
  | 3 | the same target, same token, through **dropssh v0.2.3** | **12 bytes: the banner only** |
  | 5 | a full ssh session out, using a raw client as `ProxyCommand` | `FORWARD_SSH_OK uid=0 cpu=2 mem=1983 MiB os=Ubuntu 26.04.1 LTS` |

  So Railway's KEXINIT (684 bytes) arrives intact when the client is mine, and
  never arrives when the client is dropssh's. **The fault is dropssh v0.2.3's
  forward client, not the relay.** The reverse path, which this note's PASS
  exercises, is unaffected and still passes.

  **The mechanism, measured.** In `src/connect.c` the forward branch calls
  `ws_read()`, which BLOCKS until a frame arrives. Until a frame arrives the loop
  never returns to its non-blocking `poll()` on stdin, so the client's bytes are
  never sent. Data already in the pipe when the loop first runs is delivered;
  data that arrives after the loop has parked is not:

  | first stdin byte at | bytes delivered back by dropssh |
  |---|---|
  | t=0 s | **1145** |
  | t=0.3 s | **0** |
  | t=1.0 s | **0** |

  That is the whole defect, and it is why a real `ssh` never gets its KEXINIT
  across: the server sends its banner, the loop parks in `ws_read` on the target's
  silence, and everything the client writes afterwards sits behind a stdin that is
  polled far too rarely to matter. The relay's forward path needs a **non-blocking
  or poll-driven read on the forward branch**, the same shape the reverse branch
  already uses via `ws_poll_frame()`.

  **What the earlier revision got right, and why it still read wrong.** Every
  observation in it was real: the stall was at `KEX_ECDH_REPLY`, it was not
  Railway-specific (SDF and GitHub stalled identically), and a plain HTTP GET
  also returned nothing. What it lacked was a control that shared no code with the
  thing under suspicion. Adding that control is the whole correction, and it took
  a client written from scratch rather than another argument about dropssh's source.
- This host's own egress proxy refuses port 22 with `CONNECT … 403` and allows
  443, so reaching a provider's port 22 **directly** from this sandbox is
  impossible. That is a property of this sandbox, not of the relay, and it is
  why the relay is the only route at all here.
## Appendix: the parallel implementation, judged by running it

`Nemo-010/peli-cloud` has its own `tools/ssh-relay-check.sh` and a
`research/verification/ssh-relay-2026-10-02.md`. I read both, then ran its
script unmodified on this host, because a claim about another implementation is
worth nothing until it has been executed.

**Its script exits 2 here, with no diagnosis:**

```
tar: dropssh: Cannot change ownership to uid 1001, gid 1001: Invalid argument
tar: Exiting with failure status due to previous errors
```

Three environment facts stop it, and none of them is a design error. Measured:

| # | what stops it | why | control |
|---|---|---|---|
| 1 | `tar -xzf` without `--no-same-owner` | the tarball carries uid/gid 1001; this host is uid 0 with `CapEff: 0`, so `chown` fails | dropping the flag reproduces exit 2 on its own |
| 2 | the shim is looked up at a hardcoded `/state/home/...` path | that is the sandhome data root on this host; it is not `$HOME`, so the script is not portable to a host where the two differ | the same lookup under `$HOME` succeeds here |
| 3 | its work dir defaults under the repository root, and this host's `/tmp` **dataset** refuses to execute a copied binary | `./dropbearkey` returns `Permission denied`, exit 126, which is the whole of the 126 this run exits with | the identical binary, with the identical mode `rwx------`, runs under the repo dir and is `REFUSED` under `/tmp` |

**Correction on row 3, because the first explanation was wrong.** I wrote that
`/tmp` is mode 1777 and that a world-writable parent is the cause. Measured
2026-10-02, it is not: `stat -c %a /tmp` says **755**, and the two directories
are byte-identical in mode and ownership. The difference is the filesystem.
`/proc/mounts` shows

```
rpool/home[/qaidvoid/.local/state/errand/.../tmp] /tmp        rw,relatime,xattr,posixacl,casesensitive
rpool/home/dev                        /workspace   rw,relatime,xattr,posixacl,casesensitive
```

so `/tmp` is a separate dataset from `/workspace` on the same pool, and it is
the `/tmp` dataset that refuses `execve` on a file copied into it. The
mode-1777 story was a plausible detail fitted to a real observation, and it was
wrong; the observation (same binary, same mode, one dataset refuses it) was
right and is what the table now states. **What is not established:** which part
of that dataset configuration refuses it. The practical consequence is the
same either way and is what the script has to respect - a work dir under `/tmp`
is not a work dir this server can run from.

**Its core logic is correct, and I say so plainly.** With those three
environment fixes applied and nothing else changed - its own passwd line, its
own `-Y`, its own server command, its own login name - the login succeeds:

```
ssh_exit=0 marker=MARK:0
[5860] Pubkey auth succeeded for 'root' with ssh-ed25519 key SHA256:B+Uh77RQ... from unix:0
```

So the honest summary is that its `-Y` reading and its `LD_PRELOAD` plan are
right, and this repository's earlier claim that the released `dropbear` ignores
`-Y` is **wrong** and has been removed. What this repository adds is not a
correction of its design but the three environment facts, each with a control,
plus the honest exit-status fix it lacks: its script reads the marker through
`MARK=$(... ssh ...)` and then assigns `RC=$?`, so `RC` is the status of `echo`
and a failed login would still report `ssh_exit=0`.

Two of its regression clauses are worth keeping the shape of, and are here:
`no_committed_tokens` (its work dir is gitignored and no 64-hex string may
appear in the files) and a rendered-page-is-in-step-with-its-JSON check.

## Appendix: the multi-host proof `sandbox -> vm1 -> vm2`, and where it stopped

Attempted 2026-10-02, after the forward-path correction above. **The chain was
not completed. What is recorded here is what each leg actually did.**

| leg | result |
|---|---|
| `sandbox -> relay` (reverse node) | **works.** `ssh_exit=0`, `MARK:0:Linux`, `Pubkey auth succeeded for 'root'` |
| `sandbox -> relay -> vm1` where vm1 = Railway's anonymous VM | **works**, with a from-scratch client: `RAILWAY_VM uid=0 cpu=2 mem=1983 MiB os=Ubuntu 26.04.1 LTS` |
| `vm1 -> relay` (vm1 as its own node) | **vm1 has DNS and direct egress.** `getent hosts tcp.ssh.relay.ajam.dev` resolves it, and `curl https://tcp.ssh.relay.ajam.dev/health` from vm1 returns **200**. So the leg is available. |
| `vm1 -> vm2` | **not reached.** The blocker is shipping `dropssh` to vm1. |

### Why `vm1 -> vm2` stopped, measured

A box was reached every time and `bash`, `gzip`, `xz`, `tar`, `curl`, `openssl`
and `perl` were all present, so the release should run. What did not work was
moving 3.4 MB of binary onto it:

- **Bulk stdin through the forward path stalls.** One session per chunk of base64
  with `printf`, 12 KB per session, sustained **288 KB in 217 s** across 21
  sessions and reached 816 KB before the box was reset.
- **The box is reset while the SSH identity survives.** Files written in one
  session were still there in the next (`MARKER_123` survived), but after roughly
  40 sessions `/root/poc` was gone and the welcome message returned
  `state: error, "Connection to the control plane failed"`. The upload lost the
  race.
- **`scp` does not work here at all**: `Your box closed the file transfer before
  it started`, because the box has no `sshd` for the SFTP subsystem.
- **The egress IP was never burned.** `POST /v1/mint` succeeded three times in a
  row while a raw CONNECT to the relay returned
  `HTTP/1.1 403 not on the egress allowlist`, so the refusal is the relay's
  per-burst brake on the tunnel, not an address ban. No new egress address was
  needed, and none was requested.

### What would actually complete it

Not a faster upload. vm1 already has `curl` and working egress, so the binary
needs at most **one** fetch from a URL vm1 can already reach, or a few
kilobytes of payload — the current 3.4 MB release is the wrong artefact for the
leg. A minimal forward-capable client is ~4 KB of Python, which is what the POC
uses, and that is the version to ship.

So the chain's third leg is blocked on **artefact size against a box that resets**,
not on the relay, not on egress, and not on any missing capability in vm1. That is
a narrower claim than "the chain works" and it is the one the measurements support.
